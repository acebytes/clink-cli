## Entrypoints and data flow

1. [server.py](../server.py#L163) constructs the MCP server and [18 singleton tool objects](../server.py#L258). [Tool filtering](../server.py#L169) removes names in `DISABLED_TOOLS`, except `version` and `listmodels`, which cannot be disabled. All 18 are enabled if that variable is absent. The supplied [`.env.example`](../.env.example#L172) disables six: `analyze`, `refactor`, `testgen`, `secaudit`, `docgen`, and `tracer`. Its comment listing available tools omits `clink` and `apilookup`; the registry is authoritative.
2. [main()](../server.py#L1460) always calls `configure_providers()` before serving MCP. The [configuration gate](../server.py#L543) rejects startup without at least one API-provider configuration, even if only local utility tools or `clink` will be used. A custom HTTP endpoint is accepted without an API key, so the requirement is an API configuration rather than necessarily a hosted service or paid key.
3. [call_tool()](../server.py#L759) reconstructs `continuation_id` history **before** dispatch. It then [skips ordinary model validation](../server.py#L806) for `requires_model() == False`. Otherwise it resolves `model`/`DEFAULT_MODEL`, parses `model:option`, resolves `auto` by tool category, finds the provider, creates `ModelContext`, and checks file size before executing the tool.
4. [SimpleTool](../tools/simple/base.py#L443) sends one prepared request through `provider.generate_content()`; [workflow expert analysis](../tools/workflow/workflow_mixin.py#L1437) makes its provider call at the tool-specific completion boundary. `consensus` has its own consultation path. `clink` overrides the simple-tool execution path to spawn a configured executable.
5. [Conversation memory](../utils/conversation_memory.py#L181) stores PAL turns and file references in a [process-local TTL store](../utils/storage_backend.py#L31). It reconstructs text and live file content for later calls; it is not a native CLI session manager.

Do not treat `providers/` as the only migration boundary. Provider contracts are imported by shared tool bases, model schemas, file budgets, continuation reconstruction, tool descriptions, test fixtures, setup scripts, packaging, and Docker checks. The source inventory below identifies those coupling points without removing any of them.

## Shared model selection, files, budgets, and continuation

### Model-backed calls

- Provider priority is [Google → OpenAI → Azure → XAI → DIAL → custom → OpenRouter](../providers/registry.py#L36). `auto` chooses a preferred allowed model by tool category, with sorted first-available fallback; the registry's [ultimate fallback](../providers/registry.py#L398) is `gemini-2.5-flash`, even when no provider has models. The server subsequently validates availability.
- Shared request fields are `model`, `temperature`, `thinking_mode`, `continuation_id`, and `images` ([ToolRequest](../tools/shared/base_models.py#L60)). Workflow inputs use `step`, `step_number`, `total_steps`, `next_step_required`, findings, file/context lists, confidence, hypothesis, and `use_assistant_model` ([WorkflowRequest](../tools/shared/base_models.py#L96)). Most tools retain separate MCP entrypoints rather than being clink roles.
- [ModelContext](../utils/model_context.py#L63) lazily retrieves provider capabilities. For context windows below 300,000 tokens it allocates 60% to content and 40% to response, with files/history receiving 30%/50% of content. At or above that threshold the split is 80%/20%, with files/history receiving 40%/40% of content ([allocation](../utils/model_context.py#L124)). These are heuristics, not measured tokenizer counts: `ModelContext.estimate_tokens()` uses characters/3, while [token_utils](../utils/token_utils.py#L16) uses characters/4.
- [MCP_PROMPT_SIZE_LIMIT](../config.py#L117) defaults to 60,000 characters or is calculated as 60% of `MAX_MCP_OUTPUT_TOKENS` × 4. It limits direct transport input, not a complete model context. Model capacity and file/history budgeting are separate concerns.
- Shared file helpers require absolute paths, resolve symlinks, reject dangerous system locations and home-directory roots, expand directories with exclusions, read text, and add line numbers ([path validation](../utils/file_utils.py#L282), [expansion](../utils/file_utils.py#L327)). These are reusable utilities, not provider SDK code. Some paths intentionally skip invalid files for partial success; errors are not uniformly fatal.
- Workflow steps are driven by the calling MCP client across calls, not a Python loop that repeatedly asks a model to investigate. Shared completion prepares findings, optionally embeds relevant files, builds the tool's localized/capability-augmented system prompt, validates temperature, and calls `generate_content()` with thinking mode and images ([expert call](../tools/workflow/workflow_mixin.py#L1461)). File embedding is opt-in per tool; a file path in findings does not imply its contents reach the expert.

### PAL continuation

- Threads contain UUID, parent, original tool name, initial request, turns, tool/model/provider attribution, images, and metadata ([memory models](../utils/conversation_memory.py#L151)). Default code values are **50 turns and 3 hours**, not the template's 40 turns/24 hours ([code defaults](../utils/conversation_memory.py#L120), [template](../.env.example#L151)). Successful turn writes refresh TTL. Storage survives neither server restart nor a switch to another server process.
- [History reconstruction](../utils/conversation_memory.py#L638) traverses linked threads, deduplicates file references, prioritizes newer turns, reads the current file contents, and applies model-specific file/history budgets. Thus file context is a live reread, not a historical immutable snapshot.
- No-model tools are still provider-coupled on continuation: [server.py:1175](../server.py#L1175) selects a fallback provider model and creates `ModelContext` solely to build history. The original thread's tool determines `requires_model`, rather than the newly requested tool ([server.py:1098](../server.py#L1098)). This can affect cross-tool calls, including `clink`.
- The server merges reconstructed text into `arguments["prompt"]` ([server.py:1219](../server.py#L1219)), whereas workflows consume `step`. Initial-context merging can restore missing parameters from the original tool. Consequently the broad promise of seamless cross-tool continuation needs tool-specific verification; it is not proof that a resumed workflow consumes that enhanced prompt.
- Storage locks individual `get`/`set` operations, but [`add_turn()`](../utils/conversation_memory.py#L354) performs a read–modify–write across separate operations. Concurrent updates to one thread can overwrite each other. No concurrency reproduction was run during this audit.
- Workflow instances are singletons despite the registry's “stateless design” comment. They carry mutable histories, findings, request arguments, and model context. New ordinary workflows create a new thread without resetting all instance history; see the risk table below. The stored PAL thread is not the sole source of request state.

## Clink execution audit

### Configuration and roles

[CLIClientConfig](../clink/models.py#L43) accepts `name`, command, working directory, additional arguments, environment overrides, positive timeout, roles, and optional output-file capture. Roles have prompt path, role arguments, and description. Parser/runner are fixed by [internal client defaults](../clink/constants.py#L29), not arbitrary JSON-specified adapters.

Registry load order is [bundled configs → `CLI_CLIENTS_CONFIG_PATH` → `~/.pal/cli_clients`](../clink/registry.py#L93). Paths may be files or directories; directory JSON files are sorted. Later matching client names replace the **entire resolved client**, not individual roles/flags. Client identity lookup is case-insensitive. Only `gemini`, `codex`, and `claude` are accepted ([supported-name gate](../clink/registry.py#L128)); the tool description's Qwen example does not imply a Qwen adapter exists.

Command strings are `shlex.split()` into executable words; additional/role argument strings are converted into **one** argument rather than shell-split. Relative working-directory/prompt paths resolve against the config directory; role prompts can fall back to the project root ([role resolution](../clink/registry.py#L196)). Prompts must exist, and are read afresh per call. A default role is synthesized if absent. User overrides were intentionally not read, so the table below describes shipped configuration, not the user's effective runtime flags.

Role enums are a union across clients; execution verifies the role for the chosen client. Registry data is singleton/lazy and the tool caches schema values at construction ([tool initialization](../tools/clink.py#L63)), so registry reload alone does not refresh those enums.

### Process lifecycle, context, and output

- [Command assembly](../clink/agents/base.py#L193) is executable words + internal args + configured args + role args, followed by runner-specific prompt flags and optional output-file flag. The subprocess uses `create_subprocess_exec`, not a shell; the request is sent on stdin. CLI `working_dir` comes from config, otherwise the subprocess inherits the server working directory.
- The child inherits all parent environment variables plus configured overrides ([environment](../clink/agents/base.py#L201)). Executable lookup uses the parent `PATH` via `shutil.which`, not the overridden child `PATH`. Missing executable, spawn failure, timeout, nonzero exit without successful recovery, and parser failures produce `CLIAgentError`/tool error messages. There is no unified login-required/rate-limit/error taxonomy or retry controller.
- First-call file handling validates absolute-path syntax but does not enforce workspace confinement ([validation](../tools/simple/base.py#L940)). The prompt includes path, modification time, and size ([references](../tools/clink.py#L449)); CLIs are instructed to read them. `prompt.txt` can instead supply prompt content. All clients also receive guidance describing them as “the Gemini CLI agent” ([guidance](../tools/clink.py#L441)).
- **Images are accepted but dropped.** Prompt preparation formats file references only; the [runner explicitly discards `files`/`images`](../clink/agents/base.py#L64), and no subclass adds native image flags. Image paths can be stored in PAL memory but Clink's conversation formatter emits only content/files. The `images` field alone never reaches the child as image content or a path reference.
- Default communication timeout is [1,800 seconds](../clink/constants.py#L8), overrideable per client. [Timeout handling](../clink/agents/base.py#L123) kills the immediate process, then awaits another `communicate()` with no timeout. There is no process group/session, descendant cleanup, cancellation guard, or cleanup `finally`. No semaphore/admission control bounds simultaneous CLI subprocesses or shared-workspace access.
- The [10 MiB stream-reader limit](../clink/constants.py#L9) is not a total byte cap: `communicate()` buffers complete stdout/stderr, and optional output files are read wholly. Capture files are removed only along the successful read path; spawn/template/timeout/cancel/read failures can leave them behind ([capture lifecycle](../clink/agents/base.py#L94)).
- Parsed content is limited to [20,000 characters](../tools/clink.py#L333), preferring `<SUMMARY>` or an excerpt. This does **not** bound the returned envelope: metadata pruning drops only `events`; raw payloads, Claude raw event arrays, stderr, output-file content, and error stdout/stderr can retain full text ([metadata](../tools/clink.py#L305), [pruning](../tools/clink.py#L406), [error metadata](../tools/clink.py#L425)). The argv called `sanitized_command` is merely a list copy and can include the entire Claude system prompt; it is debug-logged/returned without redaction.

### Parser and error behavior by client

| Adapter | Accepted output and extraction | Error/status limitations |
| --- | --- | --- |
| [Codex parser](../clink/parsers/codex.py#L16) | JSONL; ignores malformed/non-JSON lines, collects completed `agent_message` text; keeps events/usage metadata. | Does not require `turn.completed`; top-level `error` can become answer text when no agent message exists; no special `turn.failed` handling. Non-object nested items can raise shape errors outside `ParserError`. The runner can recover any parseable text from a nonzero exit ([recovery](../clink/agents/codex.py#L17)). |
| [Claude parser](../clink/parsers/claude.py#L16) | JSON object or array, not JSONL; array chooses first result-like object, otherwise last assistant object; extracts result/top-level text, retains session/usage/raw metadata. | `is_error` remains metadata; nested `message.content` is not extracted. Nonempty stderr can produce ordinary troubleshooting content without a text result. [Nonzero recovery](../clink/agents/claude.py#L25) can return this as `AgentOutput`. |
| [Gemini parser](../clink/parsers/gemini.py#L16) | JSON object with textual `response`; stats supply model/tokens/latency and raw payload is retained. Empty response can become explanatory content from 429/API-error/stderr evidence. | Invalid root/nested shapes can escape as type/attribute errors. [Nonzero recovery](../clink/agents/gemini.py#L20) attempts one error JSON document from combined stderr/stdout starting at the first `{`; unrelated trailing text can prevent recovery. |

Recovery hooks run [before generic nonzero rejection](../clink/agents/base.py#L152). `CLinkTool` then constructs `success` or `continuation_available` without rejecting return-code/`is_error`/recovered-error metadata ([status construction](../tools/clink.py#L222)). Thus child failure can be reported as a successful answer, although diagnostic metadata survives. Existing [Claude](../tests/test_clink_claude_agent.py#L85) and [Codex](../tests/test_clink_codex_agent.py#L53) tests explicitly expect some nonzero recovery; changing this is a behavioral-contract decision, not just parser cleanup.

### Clink conversation memory

Every request starts a fresh CLI command. PAL's UUID is not a native CLI session ID. Claude's parsed `session_id` is retained only as metadata; no adapter emits a native resume command. Clink records the already capped/summarized assistant content through SimpleTool helpers ([recording](../tools/clink.py#L225)); full native context and tool transcripts are not replayed as sessions.

On continuation, the server replays PAL text and re-reads live file contents, so “file references only” is true of first calls, not the entire lifecycle. History is budgeted against the fallback PAL provider's capacity rather than the external CLI's actual model. It can fail without provider capabilities even though a direct first CLI call bypasses provider validation. The inherited Clink prompt-size validation can also count the entire enhanced prompt rather than the server's `_original_user_prompt` ([validation](../tools/simple/base.py#L901)). Memory helpers suppress some failures: continuation creation catches exceptions and assistant recording ignores `add_turn()`'s false return ([SimpleTool helpers](../tools/simple/base.py#L637)).

No recursion marker/depth guard prevents a child CLI that loads PAL MCP from calling back into the same server. No native session routing, login probe, model capability discovery, total conversation byte/thread-count cap, or CLI concurrency controller is present in the audited execution path. These are source absences, not results of a live stress test.

## Risks, code-truth differences, and evidence limits

| Risk / difference from brief or comments | Source evidence and practical implication |
| --- | --- |
| Model-free tools exist already | Planner, docgen, tracer, challenge, apilookup, listmodels, and version do no inference; `apilookup` does not perform web search. Turning each into an unconditional CLI call would change current semantics. `version` is non-inference but still makes an upstream HTTP update request. |
| Provider startup and continuation dependency | [Startup](../server.py#L1461) requires API configuration; [model-free continuation](../server.py#L1175) uses provider capabilities. A custom local API endpoint can satisfy this; “paid API keys are always required” would overstate the evidence. Removing startup validation alone would leave continuation coupled. |
| Mutable workflow state and cache identity | Reused tool objects hold `work_history`, findings, initial request ([state](../tools/workflow/workflow_mixin.py#L69)), current arguments ([assignment](../tools/workflow/workflow_mixin.py#L618)), and model context ([assignment](../tools/workflow/workflow_mixin.py#L658)). [New ordinary workflow creation](../tools/workflow/workflow_mixin.py#L697) does not reset all accumulated state. This creates isolation/stale-state risk, especially with interleaved requests; no runtime contamination test was run. Clink's short prompt scratch assignment alone does not prove cross-request contamination because that assembly currently has no suspension point. |
| Continuation schema mismatch and non-atomic updates | The server enhances `prompt`, while workflow tools consume `step`; thread lookup uses original tool identity. Stored turn updates are separate get/set operations. Cross-tool and concurrent continuation behavior needs explicit verification. |
| Assistant-model opt-out mismatch | [Thinkdeep's trigger](../tools/thinkdeep.py#L410) never reads inherited `use_assistant_model`, unlike other workflows. Final non-certain requests can call a model despite `False`. Its summary-only expert context also differs from workflows that opt into file embedding. |
| Schema/prose mismatches | Planner's custom schema can expose/require a model despite local execution. Precommit's minimum-three schema conflicts with internal-one/external-at-most-two guidance. Tool defaults/template prose disagree on TTL/turn count. These are compatibility decisions for the design. |
| Filesystem/security boundary | `chat` can overwrite `pal_generated.code`. Precommit asks the caller to create/delete a changeset and commit; it does not execute those operations itself. Clink advertises read-only while shipped flags allow edits/approval bypass. File reference validation is not a child filesystem sandbox. |
| Non-idempotent external execution and recursion | Clink can run tool-capable agents with no recursion guard, permission enforcement, concurrency limit, process-tree cancellation, or unconditional cleanup. A repeated/recursive call can perform additional real CLI actions. Bundled role selection does not restrict capabilities. |
| Unbounded capture, metadata, and storage | Reader `limit` is not a total output cap; 20,000-character content limit excludes raw metadata and errors. Thread TTL/turn limits exist, but no global stored-byte/thread-count limit exists. These are memory/transport growth risks. |
| Errors reported as success | Recovery permits nonzero exit/error payloads to become successful tool responses, and parser shape errors are not consistently normalized. Login/rate-limit/timeout distinctions are incomplete; some memory/file failures are suppressed. |
| PII/secret exposure boundary | Child environment copies parent variables. Argv metadata is not redacted, and raw CLI outputs/stderr can be returned or logged. Role/system prompts can therefore appear in metadata; no credential values were inspected or reproduced in this audit. |
| Installed CLI compatibility is unverified | Flags, JSON contracts, native session behavior, authentication, web search availability, and sandbox effects are recorded from this pinned source. No claims are made that current installed CLIs accept every shipped flag. |

Risk & Mitigation at this approval boundary: product files are preserved and the risks above are explicit design inputs. Source inspection demonstrates the implementation paths; it does not establish installed CLI version compatibility, native account/login availability, live sandbox behavior, rate-limit behavior, descendant-process cleanup, or concurrent-request outcomes. Those require the approved mocked tests and opt-in live checks. The baseline report distinguishes actual execution from source-only conclusions.

Required next gate: review and approve the Phase 2 design before writing product code. No provider deletion, dependency change, CLI safety-flag change, project rename, or tool rewrite is performed by this audit.
